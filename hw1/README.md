پاسخ تمرین Git

سؤال ۱: تفاوت merge و rebase

دستور git merge تغییرات دو شاخه را با هم ترکیب می‌کند و معمولاً یک merge commit می‌سازد. این روش برای ادغام شاخه‌های اعضای تیم مناسب است، چون تاریخچه قبلی حفظ می‌شود.

اما git rebase کامیت‌های شاخه فعلی را روی آخرین کامیت‌های شاخه مقصد دوباره اعمال می‌کند. در نتیجه تاریخچه خطی‌تر و مرتب‌تر می‌شود. مثلاً برای مرتب کردن تاریخچه یک شاخه شخصی قبل از ادغام، می‌توان از rebase استفاده کرد.

سؤال ۲: انتخاب بخشی از تغییرات

هر hunk بخشی از تغییرات یک فایل است که در خروجی diff نمایش داده می‌شود. برای انتخاب تعاملی بخش‌های موردنظر، از دستور زیر استفاده می‌کنیم:

git add -p

با انتخاب y یک بخش وارد staging می‌شود و با n از آن صرف‌نظر می‌کنیم. این کار کمک می‌کند هر کامیت تغییرات مرتبط و مشخصی داشته باشد.

سؤال ۳: پیدا کردن منشأ خطا

دستور git bisect با بررسی مرحله‌ای کامیت‌ها، کامیتی را که باعث ایجاد خطا شده پیدا می‌کند.

git bisect start
git bisect bad
git bisect good <commit-id>

Git یک کامیت میانی را بررسی می‌کند. با دستور git bisect good یا git bisect bad نتیجه آزمایش را مشخص می‌کنیم تا جست‌وجو ادامه پیدا کند. برای مثال، اگر برنامه قبلاً درست کار می‌کرده ولی حالا خطا دارد، این روش کمک می‌کند کامیت مشکل‌ساز را سریع‌تر پیدا کنیم.

در پایان:

git bisect reset

سؤال ۴: بررسی تغییرات پیش از کامیت

۱. برای بررسی وضعیت مخزن و تفاوت تغییرات staging‌شده و نشده:

git status
git diff
git diff --cached

دستور git diff تغییرات واردنشده به staging را نشان می‌دهد و git diff --cached تغییرات آماده کامیت را نمایش می‌دهد.

۲. اگر کامیت معمولی انجام دهیم، فقط تغییرات موجود در staging ثبت می‌شوند. بنابراین تغییرات جدیدی که پس از git add در README.md ایجاد کرده‌ایم، وارد کامیت نمی‌شوند و در working tree باقی می‌مانند.

۳. برای نادیده گرفتن فایل‌های موقت، مسیر زیر را در فایل .gitignore قرار می‌دهیم:

tmp/

این تنظیم فایل‌های untracked داخل این پوشه را نادیده می‌گیرد؛ اما برای فایل‌هایی که قبلاً tracked شده‌اند کافی نیست و باید آن‌ها را از tracking خارج کنیم.

سؤال ۵: رفع merge conflict در کار گروهی

۱. این conflict به این دلیل رخ داده که هر دو شاخه یک خط را به شکل متفاوت تغییر داده‌اند و Git نمی‌تواند تشخیص دهد کدام نسخه باید باقی بماند. البته تغییر فایل‌های متفاوت یا بخش‌های جدا از هم لزوماً باعث conflict نمی‌شود.

۲. با دستور زیر فایل‌های دارای conflict را بررسی می‌کنیم:

git status

در فایل README.md، علامت‌های <<<<<<<، ======= و >>>>>>> دو نسخه متفاوت را مشخص می‌کنند.

۳. چون باید اطلاعات هر دو تغییر حفظ شوند، متن نهایی را دستی طوری تنظیم می‌کنیم که هر دو تغییر باقی بمانند و علامت‌های conflict حذف شوند. سپس:

git add README.md
git status
git diff --cached
git commit

قبل از کامیت، متن نهایی را بررسی می‌کنیم تا مطمئن شویم علامت‌های conflict باقی نمانده‌اند.

۴. برای لغو merge در حال انجام، در صورتی که Git هنوز merge را تمام نکرده باشد، از دستور زیر استفاده می‌کنیم:

git merge --abort

این دستور عملیات merge را لغو می‌کند و مخزن را به وضعیت قبل از شروع آن برمی‌گرداند.

سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

۱. چون تغییرات notes.txt وارد staging نشده‌اند و فقط می‌خواهیم همان فایل به آخرین نسخه کامیت‌شده برگردد، از دستور زیر استفاده می‌کنیم:

git restore notes.txt

این دستور تغییرات ثبت‌نشده آن فایل را حذف می‌کند و فایل‌های دیگر را دست‌نخورده نگه می‌دارد.

۲. برای خارج کردن تغییرات notes.txt از staging، بدون حذف ویرایش‌های فایل:

git restore --staged notes.txt

با این کار تغییرات از staging خارج می‌شوند، اما در working tree باقی می‌مانند.

۳. چون کامیت اشتباه روی شاخه مشترک push شده و هم‌تیمی‌ها هم آن را دریافت کرده‌اند، از git revert استفاده می‌کنیم:

git revert <commit-id>
git push

این دستور یک کامیت جدید می‌سازد که اثر کامیت اشتباه را برعکس می‌کند. برخلاف حذف کامیت و force push، تاریخچه قبلی را بازنویسی نمی‌کند و برای کار گروهی امن‌تر است.
