# تمرین HTTP

## سؤال ۱

### تفاوت نسخه‌های مختلف HTTP

- HTTP/0.9: نسخه‌ای ساده که فقط از متد GET پشتیبانی می‌کرد و فاقد Header و Status Code بود.
- HTTP/1.0: قابلیت‌هایی مانند Header، کدهای وضعیت و متد POST اضافه شدند. معمولاً برای هر درخواست اتصال TCP جداگانه‌ای برقرار می‌شد.
- HTTP/1.1: از اتصال پایدار (Persistent Connection)، هدر Host و قابلیت‌هایی مانند انتقال Chunked پشتیبانی می‌کند.
- HTTP/2: از قالب باینری و Multiplexing استفاده می‌کند تا چند درخواست از طریق یک اتصال TCP منتقل شوند.
- HTTP/3: از پروتکل QUIC روی UDP استفاده می‌کند و با مستقل‌کردن جریان‌ها، اثر گم‌شدن بسته‌ها بر سایر جریان‌ها را کاهش می‌دهد.

### دلیل استفاده از UDP در HTTP/3

UDP سربار کمتری دارد و قابلیت‌هایی مانند تحویل قابل‌اطمینان داده‌ها را خودش فراهم نمی‌کند. پروتکل QUIC این قابلیت‌ها را در لایه بالاتر پیاده‌سازی می‌کند. در نتیجه، HTTP/3 می‌تواند اتصال را سریع‌تر برقرار کند و از توقف همه جریان‌ها به دلیل گم‌شدن بسته‌های یک جریان جلوگیری کند.

## سؤال ۲

### الف) تفاوت Stateless و Stateful

در مدل `Stateless`، سرور برای پردازش هر درخواست به اطلاعات ذخیره‌شده از درخواست‌های قبلی وابسته نیست. اما در مدل `Stateful`، وضعیت تعاملات قبلی نگهداری می‌شود و می‌تواند بر پردازش درخواست‌های بعدی تأثیر بگذارد.

### ب) نوع HTTP و روش مدیریت وضعیت

پروتکل HTTP ذاتاً Stateless است؛ یعنی هر درخواست به‌صورت مستقل پردازش می‌شود. برای حفظ وضعیت کاربر در برنامه‌های وب، می‌توان از `Cookie`، `Session` و توکن‌هایی مانند JWT استفاده کرد.

## سؤال ۳

### الف) چالش مدل Client/Server

در ارتباط معمول HTTP، کلاینت درخواست را آغاز می‌کند و سرور در پاسخ به آن داده می‌فرستد. بنابراین، سرور نمی‌تواند بدون وجود سازوکار ارتباطی مناسب، مستقلاً یک پیام جدید برای کلاینت ارسال کند. این محدودیت در کاربردهایی مانند چت آنلاین، Webhook و ارسال اعلان‌های لحظه‌ای مشکل ایجاد می‌کند.

### ب) راهکارهای حل مشکل

۱. Polling

در این روش، کلاینت به‌صورت دوره‌ای از سرور درخواست می‌کند تا از وجود اطلاعات جدید مطلع شود. پیاده‌سازی آن ساده است، اما ممکن است درخواست‌های غیرضروری زیادی ایجاد کند و باعث افزایش بار سرور شود.

۲. Server-Sent Events (SSE)

در این روش، کلاینت یک اتصال HTTP برقرار می‌کند و سرور از طریق همان اتصال، اطلاعات و رویدادهای جدید را به‌صورت پیوسته ارسال می‌کند. این راهکار برای اعلان‌ها و داده‌هایی که فقط از سرور به کلاینت می‌روند مناسب است.

۳. WebSocket

با برقراری اتصال WebSocket، یک کانال ارتباطی پایدار و دوطرفه ایجاد می‌شود. در این حالت، هر دو طرف می‌توانند بدون نیاز به ارسال درخواست HTTP جدید برای هر پیام، اطلاعات ردوبدل کنند. این روش برای چت آنلاین و برنامه‌های بلادرنگ کاربرد دارد.

۴. Webhook

در این روش، هنگام رخ‌دادن یک رویداد، سرویس مبدأ یک درخواست HTTP به آدرس از پیش تعیین‌شده سرویس مقصد ارسال می‌کند. این روش برای اطلاع‌رسانی بین سرویس‌ها مناسب است، اما مقصد باید یک Endpoint قابل دسترس داشته باشد.

## سؤال ۴

اجزای URL زیر به این صورت هستند:

`ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1`

- Scheme: ss
- Username: asghar
- Password: 1234!!
- Host: ss.myproxy.com
- Port: 1234
- Fragment: shadowSocks1

## سؤال ۵

### ۱. دیتابیس سایت دچار مشکل شده و ورود کاربران انجام نمی‌شود.

کد پیشنهادی: `503 Service Unavailable`

اگر مشکل موقتی باشد و سرویس نتواند درخواست‌ها را پردازش کند، این کد مناسب است. اگر خطای داخلی غیرمنتظره‌ای رخ داده باشد که مشخصاً به معنی در دسترس نبودن موقت سرویس نیست.

### ۲. نام کاربری واردشده وجود ندارد و ورود ناموفق است.

کد پیشنهادی: `401 Unauthorized`

این کد برای زمانی مناسب است که احراز هویت انجام نشده یا اعتبارنامه‌ها معتبر نیستند. استفاده از پاسخ یکسان برای نام کاربری ناموجود و رمز عبور اشتباه می‌تواند از افشای اطلاعات مربوط به حساب‌های کاربران جلوگیری کند.

### ۳. وب‌سایت به دامنه دیگری منتقل شده است.

کد پیشنهادی: `301 Moved Permanently`

این کد برای انتقال دائمی استفاده می‌شود و آدرس جدید از طریق هدر Location اعلام می‌شود. اگر انتقال موقت باشد، می‌توان از 307 Temporary Redirect استفاده کرد.

### ۴. تعداد درخواست‌های کاربر از حد مجاز بیشتر شده است.

کد پیشنهادی: `429 Too Many Requests`

این کد نشان می‌دهد که تعداد درخواست‌های ارسال‌شده از محدودیت تعیین‌شده بیشتر است. در صورت نیاز، هدر Retry-After مشخص می‌کند که کاربر چه زمانی دوباره درخواست بفرستد.

### ۵. تمدید JWT موفق بوده و توکن جدید در Header بازگردانده شده است.

کد پیشنهادی: `200 OK`

چون عملیات با موفقیت انجام شده است، این کد مناسب است و توکن جدید می‌تواند در هدر مربوطه قرار بگیرد.

### ۶. آدرس IP کاربر در محدوده ممنوعه قرار دارد.

کد پیشنهادی: `403 Forbidden`

این کد نشان می‌دهد که سرور درخواست را دریافت کرده، اما به دلیل محدودیت دسترسی اجازه انجام آن را نمی‌دهد.

## سؤال ۶

### ۱. استفاده از سرورهای داخلی دانشگاه برای دریافت بسته‌ها به‌جای سرورهای مرکزی

راهکار: Caching Proxy / Package Mirror

در این روش، بسته‌ها روی سرورهای داخلی ذخیره می‌شوند تا کاربران دانشگاه بتوانند آن‌ها را مستقیماً از شبکه داخلی دریافت کنند. این کار مصرف پهنای باند اینترنت را کاهش می‌دهد و سرعت دریافت بسته‌ها را افزایش می‌دهد.

### ۲. تقسیم درخواست‌ها بر اساس موقعیت جغرافیایی مبدأ

راهکار: Reverse Proxy / Load Balancer با Geo-based Routing

در این روش، درخواست‌ها بر اساس موقعیت جغرافیایی کاربر به سرور مناسب هدایت می‌شوند. این کار می‌تواند تأخیر ارتباط را کاهش دهد و توزیع بار میان سرورهای مناطق مختلف را بهبود ببخشد.

### ۳. اضافه‌کردن قابلیت احراز هویت به یک سرویس قدیمی

راهکار: Reverse Proxy به‌عنوان Authentication Gateway

یک Reverse Proxy در مقابل سرویس قدیمی قرار می‌گیرد و پیش از ارسال درخواست به سرویس، احراز هویت کاربر را بررسی می‌کند. با این روش، می‌توان قابلیت احراز هویت را بدون نیاز به تغییرات اساسی در کد سرویس قدیمی اضافه کرد.
